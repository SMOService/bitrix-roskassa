# Roskassa для 1С-Битрикс

[![CI](https://github.com/SMOService/bitrix-roskassa/actions/workflows/ci.yml/badge.svg)](https://github.com/SMOService/bitrix-roskassa/actions/workflows/ci.yml)
[![PHP](https://img.shields.io/badge/PHP-7.4%E2%80%938.3-777bb4)](composer.json)
[![License: MIT](https://img.shields.io/badge/license-MIT-green.svg)](LICENSE)

Модуль платёжной системы [Roskassa](https://roskassa.net) для модуля «Интернет-магазин» (`sale`) 1С-Битрикс.

[English version](README.en.md)

## Чем отличается от типового обработчика

| | Типовой обработчик | Этот модуль |
|---|---|---|
| Когда заказ считается оплаченным | по подписи уведомления | подпись **и** подтверждение оплаты через API шлюза |
| Если уведомление не дошло | заказ остаётся неоплаченным, деньги уже у шлюза | агент сверки раз в 10 минут проходит по оплатам шлюза за 7 дней и проводит пропущенные |
| Куда приходят уведомления | общий `sale_ps_result.php`, обработчик угадывается по полям запроса | свой адрес с явным ID платёжной системы |
| Повторное или параллельное уведомление | может провести оплату дважды | блокировка на платёж и журнал оплат: одна оплата шлюза проводится один раз |
| Платёж сняли с оплаты или вернули на счёт | повтор уведомления снова его проведёт | повторно не проводится, уходит на ручной разбор |
| Смена домена шлюза | правка кода | одно поле в настройках |

Проверки уведомления: подпись (`hash_equals`), ID магазина, номер заказа, статус, признак тестового платежа, сумма (в копейках), валюта. Затем — запрос к API: заказ шлюза должен быть оплачен, создан не раньше счёта, сумма и валюта совпадают, это не тестовый заказ. Общий `sale_ps_result.php` этот обработчик не выбирает никогда: без блокировки параллельные запросы провели бы оплату несколько раз.

## Требования

- 1С-Битрикс: Управление сайтом или коробочный Битрикс24 с модулем «Интернет-магазин».
  Облачный Битрикс24 сторонние модули не поддерживает.
- PHP 7.4–8.3.
- Магазин в кабинете Roskassa: ID магазина, секретный ключ и **API-ключ**.
- Агенты на cron. Иначе сверка (до десятков запросов к API) выполняется во время запроса случайного посетителя.

## Установка

1. Скачайте архив модуля со страницы [Releases](https://github.com/SMOService/bitrix-roskassa/releases) и распакуйте папку `smoservice.roskassa` в `/local/modules/` (или `/bitrix/modules/`).
2. Админка → «Marketplace» → «Установленные решения» → «Roskassa — приём платежей» → «Установить».
3. «Магазин» → «Настройки» → «Платёжные системы» → «Добавить», обработчик **Roskassa (roskassanet)**.
4. Заполните поля (см. ниже), сохраните, проверьте оплату на небольшую сумму и только потом включайте платёжную систему.

Установщик кладёт:

- обработчик в папку пользовательских обработчиков `sale` (по умолчанию `/bitrix/php_interface/include/sale_payment/roskassanet/`);
- адрес уведомлений `/bitrix/tools/smoservice_roskassa_notify.php`;
- агент `\Smoservice\Roskassa\Reconciler::agent();` с интервалом 600 секунд.

## Настройки платёжной системы

| Поле | Обязательно | Что это |
|---|---|---|
| ID магазина | да | `shop_id`, публичный ключ магазина |
| Секретный ключ | да | подписывает форму оплаты и уведомления |
| API-ключ | да | без него модуль не выдаёт форму оплаты: подтвердить и сверить оплату было бы нечем |
| Адрес шлюза | нет | по умолчанию `https://roskassa.net` |
| Префикс номера заказа | нет | номер у шлюза `<префикс>-<ID платежа>`. Пусто — случайный префикс сайта, созданный при установке. После запуска не менять |
| Тестовый режим | нет | тестовые платежи засчитываются только в нём и только по заказам администраторов |
| ID способа оплаты | нет | сразу открыть конкретный способ (карта, СБП…) без экрана выбора |
| Язык страницы оплаты | нет | `ru` / `en` |
| Страницы успеха и ошибки | нет | полный адрес; если пусто — из настроек магазина в кабинете |
| Адрес уведомлений | нет | обычно пусто: модуль передаёт свой адрес с каждой оплатой |

На одном модуле можно завести несколько платёжных систем — например, отдельно «Карта» и «СБП» с разными ID способа оплаты.

## Как это работает

```
Покупатель → форма (подпись md5) → roskassa.net/pay/
                                       │ оплата
                                       ▼
Шлюз → POST /bitrix/tools/smoservice_roskassa_notify.php?ps=ID
         ├─ проверка подписи, магазина, суммы, валюты
         ├─ API /api/order/ (и /api/orders/ при повторных попытках) — оплачено?
         └─ PaySystem\Service::processRequest → платёж оплачен

Агент (каждые 10 мин) → оплаченные заказы шлюза с префиксом сайта:
         быстрый проход — свежие за 7 дней, полный — вся история с установки по 5 страниц за запуск
         ├─ уже в журнале → пропуск
         ├─ платёж не оплачен → проверка → проведение
         ├─ платёж оплачен другим заказом шлюза → duplicate (вернуть деньги)
         └─ платежа нет → orphan
```

Шлюз отправляет уведомление один раз и не повторяет его, поэтому сверка — не опция, а часть надёжности.

## Журналы

- **Журнал оплат** `smoservice_roskassa_credit` — каждая оплата шлюза, которую модуль провёл или отложил. Первичный ключ — id заказа шлюза, поэтому одна оплата не проведётся дважды. Статусы:
  - `credited` — проведена;
  - `mismatch` — оплачена у шлюза, но сумма, валюта или признак теста не совпали с платежом;
  - `duplicate` — повторная оплата уже оплаченного платежа, деньги нужно вернуть покупателю;
  - `review` — оплачена, но заказ отменён, платёж раньше снимали с оплаты или перевели на другую платёжную систему;
  - `save_failed` — оплата застолблена, но сайт не сохранил платёж оплаченным (громкая запись в журнале ошибок);
  - `orphan` — оплачена у шлюза, а платежа с таким номером на сайте нет.

  Всё, кроме `credited`, требует ручного разбора. Таблица остаётся после удаления модуля.
- **Журнал ошибок платёжных систем** (`b_sale_pay_system_err_log`) — отказы и нештатные ситуации с префиксом `Roskassa:`. Секреты туда не попадают.

## Стенды и копии сайта

Префикс номеров заказов хранится в настройках модуля и копируется вместе с базой. Если на копии сайта остались боевые ключи Roskassa, задайте там другой префикс в настройках платёжной системы или другие ключи: иначе номера копии и боевого сайта могут совпасть.

## Удаление

Сначала удалите платёжные системы на обработчике Roskassa — иначе установщик откажет.

## Разработка

```bash
composer install
vendor/bin/phpunit
```

Сверка проводит оплату напрямую (`setPaid` + событие `OnSalePsServiceProcessRequestBeforePaid`), без `OnSaleAfterPsServiceProcessRequest`: у неё нет HTTP-запроса. Интеграциям, которые слушают только его, нужно подписаться и на изменение оплаты.

Тесты покрывают подписи (включая сверку с алгоритмом шлюза), проверку уведомлений, сборку формы, клиент API и подтверждение оплаты. Код, который вызывает ядро Битрикса, живёт в `Handler`, `NotifyController`, `Reconciler`, `PaymentLock`.
